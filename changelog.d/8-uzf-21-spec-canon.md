- **The family spec is the canon, and the feature spec gains acceptance** (`handbooks/VERSION` `v0.8`, MINOR under the pre-1.0 carve-out; `UZF-21`'s meaning changes). For a repository that declares a product family, the canon for a feature is the family's private spec repository, `specs/<nnn>-<slug>/spec.md` at a tag, and `docs/Features/<Name>.md` becomes a generated pointer carrying only that folder path and the tag (zheref/hatsu ROSTER HR-6). A repository with no family keeps its feature docs as canon. `UZF-21` gains clauses (a)–(f) for every repository: the spec decides over the code, and the "if the spec disagrees with the code, the spec is wrong" line is retired in the three stack feature-documentation rule files; a port reads the spec, never another platform's code; the skeleton gains `## Acceptance` (`AC-{n}`, Given / When / Then) and `## Success criteria` (`SC-{n}`, measurable), so issues and PRs can cite the ids (HR-11); a multi-platform feature's platform notes become a `## Platform notes` table with one row per `AC-{n}`/`FR-{n}` id and a `port` · `adapt` · `n/a` disposition per platform, where an unported requirement is an `n/a` row with its rationale, never a missing row; and every open question names its owner and a date (HR-4). The SwiftUI, Compose and React session checklists check all of this. `UX-13` is new: navigation pattern, back behaviour, sheets and dialogs, haptics, permission prompts and typography scale adapt to the platform, while business rules, data lifecycle, copy and the acceptance outcome are mirrored from the spec. No rule id was renumbered and no token was added.
