- **The family spec is the canon, and the feature spec gains acceptance** (`handbooks/VERSION` `v0.9`, MINOR under the pre-1.0 carve-out; `UZF-21`'s meaning changes). For a repository that declares a product family (`families[]` in its `nen/repos.json`, owned and read by the planes; zheref/hatsu ROSTER HR-16), the canon for a feature is the family's private spec repository, `specs/<nnn>-<slug>/spec.md` at a tag, and `docs/Features/<Name>.md` becomes a generated pointer carrying only that folder path and the tag (zheref/hatsu ROSTER HR-6). A repository with no family keeps its feature docs as canon. `UZF-21` gains clauses (a)–(f) for every repository: the spec decides over the code, and the "if the spec disagrees with the code, the spec is wrong" line is retired in the three stack feature-documentation rule files; a port reads the spec, never another platform's code; the skeleton gains `## Acceptance` (`AC-{n}`, Given / When / Then) and `## Success criteria` (`SC-{n}`, measurable), so issues and PRs can cite the ids (HR-11); a multi-platform feature's platform notes become a `## Platform notes` table with one row per `AC-{n}`/`FR-{n}` id and a `port` · `adapt` · `n/a` disposition per platform and the `UX-13` category of each row, where an unported requirement is an `n/a` row with its rationale, never a missing row, `adapt` is admitted only in a `UX-13` adapt category and an `AC-{n}` outcome always mirrors; and every open question is an `OQ-{n}` row with its owner and a date (HR-4). Clauses (e) and (f) bind `docs/Features` canon in a repository that declares no family; in a family `spec.md`, (d)'s ids map onto the pinned Spec Kit layout (an `AC-{n}` is a numbered acceptance scenario under a `US-n`, the success criteria sit under `## Success Criteria`), a per-member difference lives in `parity.md` (`SP-6`), and an open question is an `SP-1` marker settled by an `SP-12` `CL-nnn`. A mirror category outside `UX-13`'s lists, such as business rules, is a valid Category value. The new findings' severities sit in `uzf-core.md`'s *Severity guidance* table, not in the rule bodies. The SwiftUI, Compose and React session checklists check all of this. `UX-13` is new: navigation pattern, back behaviour, sheets and dialogs, haptics, permission prompts and typography scale adapt to the platform, while copy and the acceptance outcome as the user sees it are mirrored from the spec; business-rule and data-lifecycle divergence stays with `UZF-21(b)`/`(e)` in the architecture reviewer's lane. No rule id was renumbered and no token was added.
