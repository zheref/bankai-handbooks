- **The spec authoring handbook and the capture reader appendices** (`handbooks/VERSION` `v0.10`, MINOR). `handbooks/spec/authoring.md` is new. It carries the `SP-{n}` family, `SP-1`–`SP-14`, for writing and reviewing a product family's spec folders (zheref/hatsu ROSTER HR-6; the capture skill is `dowsing-chain`, HR-12). Ownership is split with `UZF-21`: `UZF-21(a)`/`(b)`/`(d)`/`(e)` own the folder's existence, the pointer, the revise-first rule and `spec.md`'s Acceptance, Success-criteria and Platform-notes sections, and the `SP-` family owns the folder's authoring grammar. The rules cover the following. Every requirement line ends in a citation (`[src: …]` at a commit, or `[ruled: CL-nnn]`) or in one marker, and recapture writes `[STALE @ <old sha>]`. There are three confidence tiers, with `declared` earned only by a quoted test assertion or the maintainer's typed answer, and an inferred row is never a MUST or a success criterion. Source text sits only inside fenced `source-data` blocks (`SEC-15`). No framework vocabulary appears in `spec.md` or `data-model.md`. Each requirement and member gets one `parity.md` state, spelled as the capture skill writes it: the handlings `present` · `mirror` · `map` · `drop-with-note` · `target-only`, and the open sub-states `absent` and `differs`, which block dispatch until a `CL-nnn` ruling. A build cites the spec at a pinned commit, citing `UZF-21(b)` for revise-first. Convergence appends, ids never renumber (the id forms are `UZF-21(d)`'s, and `PT-{n}` is cited, never minted), and a reversal is a supersedes line. Clarification is bounded at five questions per round and three rounds per run unless the spec repository declares `spec.clarify.maxQuestions` / `maxRounds` otherwise, and answers are kept verbatim under a dated session. Checklists are ticked by the reviewer, never the author. Completeness is `covered/total` per kind for a spec folder or a capture (`SP-14`). An informative table names the 14 capture row kinds. `QA-26` is reserved and was never in force: the completeness rule drafted there became `SP-14`. The SwiftUI, Compose and React stack handbooks each gain an *Appendix — capture reader* mapping file suffix → UZF concept → row kind, with no new stack id. The Compose appendix cites the `rules/README.md` KT registry, and the pre-existing numbering collision is #11. No rule id was renumbered and no token was added. Flow impact: only a family spec repository loads `SP-{n}`, resolved live from a checkout at the pin; no consumer mirror regenerates; a product repository's own build and review are unchanged.
