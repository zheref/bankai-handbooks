# 04 — Services & Dependencies

## Repo-specific placeholders

- None — this rule carries no repo-specific paths, hosts, target, or product names. Example domain types (`ProfileClient`, `Profile`, …) are illustrative, not repo config.

Implements `UZF-16` (external systems behind a DI'd Service with a stub) and
`UZF-17` (wire types + Mapper); tightened for TCA by `SW-15` and `SW-16`.

## The default shape: `@DependencyClient` (`SW-15`)

```swift
import ComposableArchitecture

@DependencyClient
public struct ProfileClient: Sendable {
    public var fetchProfile: @Sendable (_ id: UUID) async throws -> ProfileResponse
    public var updateDisplayName: @Sendable (_ id: UUID, _ name: String) async throws -> ProfileResponse
}

extension ProfileClient: DependencyKey {
    public static let liveValue = ProfileClient(
        fetchProfile: { id in /* real impl */ },
        updateDisplayName: { id, name in /* real impl */ }
    )
    public static let previewValue = ProfileClient(
        fetchProfile: { _ in .preview },
        updateDisplayName: { _, name in .preview(name: name) }
    )
    // testValue is auto-generated by @DependencyClient — every closure becomes
    // `unimplemented("ProfileClient.fetchProfile")` which fails the test
    // if called unexpectedly.
}

extension DependencyValues {
    public var profileClient: ProfileClient {
        get { self[ProfileClient.self] }
        set { self[ProfileClient.self] = newValue }
    }
}
```

### Why `@DependencyClient` over hand-rolled

- Generates the `testValue` for free → no team can ship a missing one.
- Generates `Sendable` conformance and `init` correctly.
- Compiler enforces that every closure has a `@Sendable async throws` shape.
- Removes the temptation to write `fatalError("Implement in production")` in `liveValue` (`SW-15` — no `fatalError` in a `liveValue` closure).

## Required variants (`SW-15`)

| Variant | Mandatory? | When to ship it |
| --- | --- | --- |
| `liveValue` | yes | Production behavior. If an operation isn't implemented yet, **omit** it from the initializer — the macro fills in an `unimplemented` closure. |
| `previewValue` | yes | Synthetic, deterministic data for Xcode previews. Allowed: a short `Task.sleep` for realism. |
| `testValue` | auto-generated | Don't write by hand. Override per-test with `withDependencies { $0.profileClient.fetchProfile = { _ in … } }`. |
| `stubbedValue` | optional | When QA/manual testing benefits from a fixture-driven mode. Reads JSON from `Bundle.main`. |

## When to wrap in a Repository (`UZF-16`)

A `Repository` is the **only** stateful artifact in the service tier. Wrap a Client in a Repository when:

- Multiple operations share a non-trivial cache (e.g. a `currentProfile` invalidated by writes).
- You need to coordinate two clients (e.g. `ProfileClient` + `Database`).
- You need to fan-out events (e.g. publish profile changes to multiple subscribers).

Otherwise, **don't**. Direct `@Dependency(\.profileClient)` from the Producer is the default. Empty/placeholder Repositories are forbidden (`UZF-16`).

```swift
@Observable
public final class ProfileRepository: Sendable {
    @ObservationIgnored @Dependency(\.profileClient) private var client
    @ObservationIgnored @Dependency(\.profileDatabase) private var db

    public private(set) var current: Profile?

    public func refresh() async throws { /* hits client, writes db, sets current */ }
}
```

Note: Repositories are still injected via `@Dependency` — they get their own `DependencyKey`. They are *not* `@StateObject`s.

## System dependencies (`SW-15`)

Always prefer TCA's first-party deps over raw Foundation:

| Don't write | Write |
| --- | --- |
| `Date()` | `@Dependency(\.date.now) var now` |
| `UUID()` | `@Dependency(\.uuid) var uuid` |
| `Task.sleep(for:)` for debouncing | `@Dependency(\.continuousClock) var clock` + `.debounce(id:for:clock:)` |
| `URLSession.shared.data(from:)` | Wrap in a `…Client` operation; the operation may call URLSession. |
| `UserDefaults.standard` | `@Shared(.appStorage("key"))` or a `…Store` Client |
| `FileManager.default` | A `FileStore` Client |

## Granular dependency segregation (`UZF-16` — segregation by feature, not domain)

A Feature should declare only the dependencies it uses. **Reject** code that drags in a god-Client containing twelve unrelated operations. Split:

- ✅ `@DependencyClient struct ProfileClient` with `fetch`, `update`.
- ✅ `@DependencyClient struct AvatarClient` with `upload`, `delete`.
- ❌ `@DependencyClient struct UserClient` with `fetchProfile`, `updateProfile`, `uploadAvatar`, `deleteAvatar`, `fetchPosts`, `likePost`, …

If two features share a client today and one will diverge tomorrow, that's fine — split when they diverge, not preemptively.

## Wire format vs. domain (`SW-16` implements `UZF-17`; see also `UZF-8`)

Every operation that crosses the network or DB boundary returns a `…Response` (or `…Record`) type, not a domain `Profile`. The conversion happens in a `Mapper` called from the Producer:

```swift
let response = try await client.fetchProfile(id: id)
guard let profile = response.asDomain else { return .failure(.unknown(message: "Malformed payload")) }
return .success(profile)
```

`Profile` never gets a `Codable` conformance. `ProfileResponse` never gets a SwiftUI `Identifiable` conformance (`SW-16`).
